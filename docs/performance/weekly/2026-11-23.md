# Weekly performance — 2026-11-23

Honest Amber vs Node vs Bun cycle. The comparison point for last week's
optimization is the after table in `docs/performance/weekly/2026-11-13.md`
on PR #328 (that file is not on main). Numbers below come only from
`benches/honest/run.sh` on this machine in this session. Historical
`docs/STAGE_*` and `docs/*PERFORMANCE*` files are not used as current facts.

Ratios are amber/peer. Above 1 means Amber is slower or used more CPU. `inf`
means the peer median was 0 while Amber was not. Medians use repeated samples
after discarded warmups (page cache, and Amber's on-disk startup snapshot if
the first `eval` creates one).

The open optimization is still the 2026-11-13 change: amber:* product modules
that scripts open with `require` install on first require. This week rebases
that commit onto main `93b30d59` (#327) and remeasures it. No second gap was
edited.

Peer and tree differences versus 2026-11-13: Node stays v26.13.1. Bun is
1.4.5 (published 2026-11-19; that report used 1.4.4). The kernel string, CPU
class, and MemTotal match that report's machine, but this is a new VM. Main
also contains the wasmtime 49.0.5 bump, which is in both the before and after
binaries below, so it is not the before/after delta.

## Change

Rebased `3a5afa47` onto `93b30d59`. The patch still applies cleanly. No
further source edit.

`install_core_apis` does not call the require-only amber:* product setup
functions. The first `require('amber:…')` (and the builtin id without the
prefix) installs that one surface on the current context. Node builtins, the
extended Web surface, and `amber:wasm` stay on the startup path. `amber:wasm`
still patches `WebAssembly.Memory` and publishes global `wasm`. `amber:ai`
property accessors `require` the matching module.
