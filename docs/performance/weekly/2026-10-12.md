# Weekly performance — 2026-10-12

First honest Amber vs Node vs Bun cycle. There is no earlier weekly report.
Numbers below come only from `benches/honest/run.sh` on this machine. Historical
`docs/STAGE_*` and `docs/*PERFORMANCE*` files are not used as current facts.

Ratios are amber/peer. Above 1 means Amber is slower or used more CPU. `inf`
means the peer median was 0 while Amber was not. Medians use repeated samples
after discarded warmups (page cache, and Amber's on-disk startup snapshot if
the first `eval` creates one).

## Ranked gaps (baseline)

1. **Cold startup, especially `--version`.** 45.4 ms vs Node 2.8 ms (16×) and Bun 0.9 ms (48×). This floor sits under eval, script, 1MB read, and cold HTTP. Highest user impact for an agent-tool CLI, largest ratio vs the stronger peer, and fixable without a V8 upgrade. **Chosen.**
2. **Idle HTTP CPU.** A listening `http.createServer` used 200 ms of CPU in a 3s quiet window (about 7% of one core) vs 0 ms for Node and Bun. Sandbox `session` and a far `setTimeout` were already 0 ms, so this is the HTTP keep-alive loop, not the timer park. Fixable later (longer park plus less idle `malloc_trim` / `low_memory_notification`). Not this week's change.
3. **Eval / cold HTTP vs Bun.** Bun eval is ~3 ms and cold HTTP ~19 ms. Most of Amber's absolute gap was the startup floor in row 1. After that floor is removed, catching Bun's remaining eval gap is an engine/image-size problem (V8 upgrade or a new bundler), which is out of scope for one week.
4. **Not a gap:** warm HTTP hello (Amber median 0.07 ms vs Node 0.17 ms), `fs.readFileSync` of 1MB beyond process startup, sandbox-session idle CPU, and far-`setTimeout` idle CPU.

## Hypothesis

Every CLI start, including `amber --version`, called `read_standalone_payload`, which copied the entire ~83MB release executable into a `Vec` to look for an `AMBER_STANDALONE` trailer.

Checked before editing, on the baseline binary:

- `amber --version` `/usr/bin/time -v`: wall 43.1 ms, user 0.00 s, system 0.04 s, max RSS 93376 kB, 22035 minor page faults.
- `AMBER_TRACE_STARTUP=1 AMBER_PROFILE_STARTUP=1 amber eval "1+1"` starts its clock only after that read and clap parse. `cli_ready` was 0.003 ms and `script_executed` was 9.6 ms (isolate 1.15 ms, core APIs 5.31 ms, extended APIs 1.08 ms).
- Eval wall median 55.1 ms is about the 45 ms `--version` floor plus that ~10 ms of runtime setup. Disabling the startup snapshot (`AMBER_DISABLE_STARTUP_SNAPSHOT=1`) still took 53.4 ms, so the snapshot was not the 45 ms.

## Change

`read_standalone_payload` no longer slurps the executable. A normal Linux/Windows binary only has the last 16 bytes checked for the SEA magic. A Mach-O image reads the header and load commands (capped) and, only when an `__AMBER` segment exists, the trailer inside that segment. A real SEA payload is still read in full, and a bad trailer still fails closed. `find_standalone_trailer` on an in-memory image is unchanged.
