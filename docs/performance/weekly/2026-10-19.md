## Ranked gaps (baseline)

1. **Idle HTTP CPU.** A listening `http.createServer` with no timers used 200 ms of CPU in every 3 s quiet window (about 7% of one core) vs 0 ms for Node and 0–10 ms for Bun. Sandbox `session` and a far `setTimeout` were already 0 ms, so this is the HTTP keep-alive loop, not the timer park. Largest user-visible gap for an agent-tool sandbox that sits on an open port, and fixable without a V8 upgrade. **Chosen.**
2. **Eval / script vs Bun.** Eval is 14.3 ms vs Bun 2.6 ms (5.41×), tiny script 19.6 vs 3.1 ms (6.38×). Amber already beats Node on both. Closing the Bun gap is an engine or image-size problem (V8 upgrade or a new bundler), which is out of scope this week.
3. **Startup `--version` vs Bun.** 2.6 ms vs 0.9 ms (2.92×), and faster than Node (2.8 ms). The absolute gap is ~1.7 ms, much smaller than the idle-CPU gap, and the old ~45 ms floor is still gone.
4. **Not a gap:** warm HTTP hello (Amber median 0.08 ms vs Node 0.18 ms), cold HTTP vs Bun (21.2 vs 20.3 ms, 1.05×), `fs.readFileSync` of 1MB beyond process startup, sandbox-session idle CPU, and far-`setTimeout` idle CPU. Release binary growth since last week (~664 KB) did not show up as a startup regression.

## Hypothesis

The keep-alive loop after `http.createServer` slept with `park_timeout(1ms)` and, once idle, ran `low_memory_notification` three times plus Linux `malloc_trim` every 250 ms. That poll, not the listen itself, is the ~200 ms.

Checked on the baseline binary before editing, on a quiet `http.createServer` that had already answered once:

- 3 s window: user+sys 230 ms (`/proc/<pid>/stat`, 21 user ticks + 2 sys ticks at `CLK_TCK=100`), voluntary context switches +2816, nonvoluntary +0.
- `strace -c` over the same kind of window: 5680 `futex` calls and 424 `madvise` calls (plus a handful of `brk` / `munmap`). About 2800 wakes in 3 s is a 1 ms park. `madvise` syscall time was only ~1.6 ms; the rest of the CPU is userspace work on each wake (pump, microtask checkpoint, and the idle compaction).

A far `setTimeout` with no server stays on the timer-thread condvar and was already 0 ms, which matches last week's split.

## Change

When the keep-alive turn has nothing to pump, a quiet listener (no pending or scheduled timer, no `fs.watch`, no open WebSocket, no active `net` client, inspector not armed) parks for 8 s instead of 1 ms. HTTP accept and `net` accept already call `wake_http_dispatch_thread`, so the next request does not wait for that watchdog. Timers, watchers, WebSockets, active client sockets, and `--inspect` still use the 1 ms poll, because those events are drained by pumping rather than by an unpark.

Idle compaction is at most one `low_memory_notification` plus one `malloc_trim` (Linux) or zone pressure relief (macOS) per 30 s, instead of three notifications and a trim every 250 ms. The single compaction before the keep-alive loop still runs. Windows does not call `malloc_trim`; that `cfg` split is unchanged.

## Explicitly not changed

- V8 flags, heap limits, and the startup-snapshot bytes.
- Which Node/Web APIs are installed on first execute.
- `fs.readFileSync` and the warm HTTP request path.
- The 1 ms poll while a timer, `fs.watch` / `watchFile`, an open WebSocket, an active `net` client, or `--inspect` is keeping the loop awake. Those sources are still pumped rather than unparked.
- The non-HTTP timer park (`setTimeout` with no listener was already 0 ms CPU).
- Year-2 roadmap issues #100–#103, Dependabot PRs, and open PRs #239, #241, #242, #244.
