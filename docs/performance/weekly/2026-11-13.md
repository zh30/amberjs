# Weekly performance — 2026-11-13

Honest Amber vs Node vs Bun cycle. The weekly runs for 2026-10-26, 2026-11-02,
and 2026-11-09 were skipped, so the comparison point is
`docs/performance/weekly/2026-10-19.md` (that report's after table, which is
the tree after the quiet-listener park). Numbers below come only from
`benches/honest/run.sh` on this machine in this session. Historical
`docs/STAGE_*` and `docs/*PERFORMANCE*` files are not used as current facts.

Ratios are amber/peer. Above 1 means Amber is slower or used more CPU. `inf`
means the peer median was 0 while Amber was not. Medians use repeated samples
after discarded warmups (page cache, and Amber's on-disk startup snapshot if
the first `eval` creates one).

Peer versions moved since 2026-10-19: Node 26 became Active LTS (Lithium) on
2026-10-28, and Bun published 1.4.4 on 2026-10-22. Absolute milliseconds versus
that report therefore mix a new machine kernel with new peers. The before/after
columns below are the same Node and Bun on this machine.

## Ranked gaps (baseline)

1. **Cold eval / script versus Bun.** Eval is 13.4 ms vs Bun 2.7 ms (4.89×) and still faster than Node (19.5 ms). The floor sits under tiny script, 1MB read, and cold HTTP. About 1.9 ms of it is amber:* product binding install that an agent script does not touch until `require`. That slice is binding work, fixable without a V8 upgrade. **Chosen.** `amber:wasm` (0.28 ms) is not in that slice: it patches `WebAssembly.Memory` and publishes global `wasm` for scripts that never call `require`.
2. **Startup `--version` versus Bun.** 2.2 ms vs 1.0 ms (2.13×), and faster than Node (2.7 ms). The absolute gap is ~1.2 ms. Closing it means a smaller image, which is the bundler-sized change called out of scope.
3. **Remaining eval time after the product slice.** Isolate create is ~1.2 ms and Node/Web install is ~4.7 ms, spread across dozens of calls with none above 0.82 ms. Deferring `fetch` / `Blob` / the rest of the Web surface on a source scan is unsound for dependency bodies. That remainder is not this week's edit.
4. **Not a gap:** warm HTTP hello, cold HTTP versus Bun (0.93×), `fs.readFileSync` of 1MB beyond process startup, sandbox-session idle CPU, far-`setTimeout` idle CPU, and idle HTTP on the quiet pass (the 2026-10-19 park still holds).

## Hypothesis

Cold `eval` spends about 1.9 ms inside `install_core_apis` building amber:* product objects (`ai`, `db`, `std`, `tools`, and the smaller siblings) that an agent script reaches only through `require`, so installing them on first require removes that cost from startup, read, and cold HTTP.

Checked on the baseline binary, five `AMBER_PROFILE_STARTUP=1` evals: median `install_core_apis` 6.0 ms. The require-only product calls summed to 1.90 ms (`std` 0.32, `ai` 0.28, `tools` 0.19, `mcp` 0.19, `bus` 0.17, and the rest at or below 0.13). `amber:wasm` was 0.28 ms and stays eager. `crypto` was 0.02 ms. Extended Web install was a separate 1.1 ms and was left on the startup path.

## Change

`install_core_apis` no longer calls the require-only amber:* product setup functions. The first `require('amber:…')` (and the builtin id without the prefix) installs that one surface on the current context and then returns the same global the eager path used to publish. A second require in the same context does not install again. Node builtins (`fs`, `http`, `crypto`, …), the extended Web surface (`fetch`, Blob, streams, …), and `amber:wasm` are still installed before the script runs. `amber:wasm` stays eager because it patches `WebAssembly.Memory` (`asUint8Array`, `getPointer`, `createZeroCopyBuffer`, …) and publishes global `wasm` for scripts that never call `require`.

`amber:ai`'s `weights` / `tools` / `kv` / `bus` / `grammar` / `checkpoint` accessors now `require` that module, so the first property read still loads it.
